Skill vs prompt

跟「每次重貼 prompt」差在三件事

差別一

存在雲端

指令存在 Claude 雲端,不用自己維護一份越長越亂的 prompt 清單。

差別二

自動觸發

不必手動上傳,Claude 看你輸入的內容,自己判斷要載入哪個 Skill。

差別三

結構更有彈性

可拆成「前置作業／執行步驟／輸出格式／自查清單」四段,變成可維護的工作流。

把同一件事做 10 次以上的人,Skill 比 prompt 划算。一次設定、之後自動生效——等於把工作流的記憶,從你身上轉到 Claude 身上。

第一個 Skill 挑什麼

挑一件重複性高、步驟固定、格式固定的任務

  • 採訪逐字稿濃縮成社群貼文

最容易踩的坑

給模糊答案——Claude 不會通靈

✗ 模糊,沒意義

「希望週報簡潔」

對 Claude 來說無法執行——它不知道你的「簡潔」長什麼樣。

✓ 具體,可檢查

  • 每個段落最多 3 句話
  • 結論放最前面
  • 別用「值得注意的是」這類開場白
把抽象標準拆成可檢查的條件。回答越具體,做出來的 Skill 越能用。

個人化偏好走另一條路

Skill 是「我要做什麼」;Profile instructions 是「我是誰」

Skill

處理「動作」——這件事怎麼做。自動觸發、可有多個。

Profile instructions

處理「你是誰」——角色、語氣偏好、寫作禁忌。自動套用到所有對話,不必每次提醒。

位置:左下角頭像 → Settings → General →「Instructions for Claude」文字方框。它和 Skill 各走各的,不會互相打架。
複利:下一期 Cowork/Code 時,同一份內容可直接搬成本機的 CLAUDE.md(AI 每次工作前必讀、跨 session 持久)——越早建立越省時。

可照抄 · 讓 Claude 用 20 題訪談你

一段 prompt,倒過來建立你的 Profile

你的任務是替我建立一份 profile instructions 文字,會被貼到 Claude.ai 的 Settings → General → Instructions for Claude,自動載入到我所有 Chat 對話。 你的工作分兩步: 1. 用 AskUserQuestion 元件訪談我(共 20 題),一次只問一題 2. 把答案整理成純 Markdown,總長度壓在 500 字以內 【訪談規則】我可選選項或選「Other」;回答太模糊要追問要具體例子;不要接受「我希望寫得清楚」這種抽象答案,要追問「清楚在你的工作裡長什麼樣子?」
第一次跑約 20–30 分鐘,但這份結構化內容價值很高——之後能直接變成 CLAUDE.md。下一頁看題綱。

20 題訪談題綱(可依角色微調)

六個面向,問出「真正的你」

我是誰(3)
  • 做什麼工作、角色、產業
  • 為誰工作(客戶/團隊/讀者)
  • 好的工作週長什麼樣
我怎麼工作(4)
  • 每天用哪些工具、怎麼用
  • 典型任務的步驟
  • 審稿/品管流程
  • 「完成」的標準是什麼
什麼是好產出(4)
  • 最近做最好的一份、為什麼好
  • 頂尖 vs 平庸差在哪
  • 看到好作品你在反應什麼
  • 要判斷你的作品該看什麼
我討厭什麼(4)
  • 一個爛作品、為什麼爛
  • 看了皺眉的套路/捷徑
  • Claude 不對勁通常錯哪
  • 絕不希望出現的寫法
我的規則(3)
  • 絕對不做的硬底線
  • 每份產出 2–3 個不可妥協條件
我的觀點(2)
  • 多數同行會反對的信念
  • 被過譽/被低估的工具方法

訪談完的輸出格式

整理成純 Markdown,500 字以內

# ABOUT ME ## 我是誰 ## 我怎麼工作 ## 什麼是好的產出 ## 我討厭什麼 ## 我的規則 ## 給 Claude 的指令(10 條編號規則)
不要保留原始問答逐字稿,要從答案中萃取模式;不需要 YAML frontmatter(profile 是純文字方框,不是 Skill)。結構與標題請保留——未來原封不動搬進 Cowork/Claude Code 的 CLAUDE.md。
Claude Skills 初心者指南 · 單元二
為什麼要精簡

控制在 500 字以內、4–6 段

Profile instructions 每次新對話 Claude 都會讀一次。太長有兩個副作用:

① 吃對話額度

你打的字、Claude 回的字,加上這份檔案,三者共用同一個工作記憶空間——越長越吃資源。

② 規則自相矛盾

規則一多就容易打架,同一份檔案兩條規則衝突,Claude 不知道該聽哪個。

刪減判準:「這句話 Claude 看了會改變行為嗎?」不會就刪。回頭砍掉抽象敘述,只留具體規則。

FROM WORKS TO WORKS WELL

單元三｜讓 Skill 從能用到好用

frontmatter 兩欄、正文四區塊、觸發率的兩個關鍵。

Claude Skills 初心者指南
官方最小結構

兩欄 frontmatter,決定 Skill 好不好用

--- name: [lowercase-identifier-with-hyphens] description: [what-the-skill-does-and-when-to-use-it] ---

name

小寫字母 + 連字號。例:weekly-report。

description(關鍵)

兩件事合一:這個 Skill 做什麼 + 什麼時候該用。看似簡單,卻決定 Skill 會不會被正確觸發。

實際建立 Skill,還是建議透過 Claude(skill-creator)來做,不要自己硬寫。
Claude Skills 初心者指南 · 單元三
成熟 Skill 正文

四區塊「四件套」,比只有指令穩定得多

1

前置作業

Skill 啟動時先做什麼:讀哪個檔、確認哪個條件。

2

執行步驟

任務的標準動作,一步一步寫清楚。

3

輸出格式

產出物長什麼樣:結構、長度、禁用詞。

4

自查清單

產出後 Claude 要自己檢查哪些事。

四件套不是硬性規定,但實測下來,有這四段的 Skill 明顯比只有指令的穩定。
Claude Skills 初心者指南 · 單元三
Skill 不啟動?

你的 Skill 好不好用,description 佔 80%

寫不好 Skill 就不會啟動,你以為它壞了,其實是 Claude 根本沒認出該用它。
關鍵一 · 直接問 Claude:「你什麼時候會用這個 Skill?」Claude 會告訴你它認定的觸發時機,你一看就知道哪裡定義不清。認出問題 → 跟 Claude 對話修改 → 重新上傳,就能解決大部分觸發問題。
注意:不要自己打開 .md 檔手動改,請告訴 Claude 怎麼改。
Claude Skills 初心者指南 · 單元三
觸發率關鍵二

寫清楚「不要用在哪」(negative trigger)

大家反射性寫「這個 Skill 用來做 X」,但更關鍵的是寫清楚「不要用在哪」。

✗ 只寫正面

linkedin-post 的 description 只寫「用來生成 LinkedIn 貼文」——你請 Claude 摘要文件時它也可能跑出來,因為「寫東西」和「生成貼文」在 AI 眼中可能重疊。

✓ 加反向限制

加一句「請勿用於部落格文章、電子報、email 或一般摘要任務」。Skill 才會只在該出現時出現。

各自適合什麼

Projects 放靜態知識,MCP 連活資料

Projects · 靜態參考

  • 品牌指南、模板、政策文件
  • Claude 會查閱、但不一定執行動作
  • 適合長期客戶、追蹤中的研究、持續產品線

MCP · 外部活資料

  • GitHub 撈今天的 commit
  • Gmail 看新信、行事曆查空檔
  • Control Chrome 查資料、Notion MCP 改內容
MCP(模型脈絡協定)就是 AI 跟外部服務的接線標準。要 Claude 操縱哪個第三方軟體,就打開對應的 MCP。

怎麼選?兩個快速判準

新任務該用哪個工具,問兩句就知道

判準一

這件事我會做幾次?

  • 做幾次就停 → 直接開新對話
  • 長期反覆(如每週寫週報)→ 做成 Skill
判準二

Claude 需要哪份資料?

  • 穩定不變的參考(品牌指南、合約模板)→ 放 Project
  • 當下實時資料(最新銷售、本週 commit)→ 接 MCP
本期為什麼專注 Skills?對多數人,Skills 是入門 CP 值最高的工具。
