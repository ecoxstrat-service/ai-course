先想清楚:為什麼是 LINE

員工和客戶早就住在 LINE 上了

要導入一套新工具,最大的成本從來不是開發,而是「請大家改用另一個 App」。
LINE 的價值在於:那個介面,大家每天已經打開幾十次——不必再教、不必再裝。

零安裝、零學習

不用開發 App、不用教操作,傳訊息大家都會。

入口思維

把 LINE 當「門」,後面接你真正的系統與資料庫。

雙向都能通

使用者傳訊息進來、系統也能主動推播出去。

官方帳號可控管

用 LINE 官方帳號的 Messaging API,權限、額度、紀錄都在你手上。

在看案例之前,先花一分鐘認識背後共用的三個「積木」。
共用的技術底層

所有 LINE 應用,都是這三個積木組出來的

積木 1 · 收

Webhook 接收

使用者一傳訊息,LINE 就把事件「推」到你設定的網址。這是系統聽見使用者的耳朵。

  • 文字、圖片、檔案、貼圖都收得到
  • 務必先驗簽確認真的來自 LINE
積木 2 · 即時回

Reply 回覆

收到訊息後,用當下拿到的一次性「回覆票券」立刻回一則訊息。免費、但只在短時間內有效。

  • 適合:回答、給連結、確認收到
  • 票券過期或用過就失效
積木 3 · 主動推

Push／Multicast 推播

不必等使用者開口,系統主動送訊息。單發用 Push、群發用 Multicast(一批最多 500 人)。

  • 適合:公告、提醒、每日早報
  • 會計入官方帳號的訊息用量
記住這三個動作:收(Webhook)、即時回(Reply)、主動推(Push／Multicast)——後面兩個案例,都是它們的排列組合。
看懂資料怎麼流

一則訊息,在背後跑完的五站

1

使用者出手

在對話或群組傳訊息、貼檔案、按連結。

2

LINE 平台轉發

LINE 把事件透過 Webhook 送到你的系統。

3

驗簽 + 辨識

確認來源可信,對出「這是哪位使用者」。

4

你的系統處理

查資料庫、分類、存檔、算結果——真正的商業邏輯在這裡。

5

回到使用者

用 Reply 或 Push 把結果送回 LINE。

關鍵觀念:LINE 只是「門面」,真正做事的是門後面你自己的系統與資料庫。門好開,但價值在門後。

CASE B · 對內部

案例 B｜把 行政流程 搬進 LINE

ECOxSTRAT 自家的營運系統(OPS),把「綁定身分、打卡、公告、每日早報」全部做進員工天天在用的 LINE 裡。
一個官方帳號,四種功能

員工不用再開系統,在 LINE 就搞定

功能 1

綁定身分

把 LINE 帳號和員工資料對上,之後系統才認得你。

功能 2

GPS 打卡

傳「上班」,拿到連結、定位、完成上下班打卡。

功能 3

公告推播

公司公告一發佈,綁定員工同步在 LINE 收到。

功能 4

每日早報

每天早上自動送來今天／明天的行事曆摘要。

同一支官方帳號,對應的正是三積木:打卡走收+回、公告走群發推、早報走排程推。
功能 1 · 綁定

第一步:讓系統認得「你是誰」

1

加好友

員工把公司官方帳號加為好友。

2

傳「綁定」

Bot 回一條專屬綁定連結。

3

登入系統

用自己的員工帳號登入確認身分。

4

對上資料

系統把 LINE 身分和員工資料綁在一起。

為什麼要綁定?因為LINE 傳來的只是一個匿名代碼,不是姓名。綁定之後,系統才知道打卡的、收公告的是哪位同事。
安全原則:一個 LINE 身分只能綁一位員工,綁定連結應為短效、用過即失效。
功能 2 · 打卡

傳兩個字「上班」,就開始打卡

  • 傳「上班／下班／補卡」,Bot 回一條短效連結
  • 開連結→授權 GPS→座標送回系統
  • 系統寫入打卡紀錄,回報結果
為什麼用短效連結而不是直接打卡?
因為連結會過期(例如 30 分鐘),就算被轉傳也無法冒用——安全和方便的平衡點。
功能 3 · 公告

公告發一次,大家同步收到

管理者發佈公告
在後台按「發佈」
↓
系統群發(Multicast)
一批最多 500 位,自動分批
↓
在職且已綁定的員工
在 LINE 收到標題 + 連結

做對一件事:不重複發

  • 只有第一次發佈時推播
  • 事後編輯公告不會再發一次
  • 只發給在職且已綁定的人
  • 需要安靜更新時,可選不推播
推播很方便,但「發幾次」比「能不能發」更重要——重複轟炸,員工就會關通知。
功能 4 · 每日早報

每天早上 08:00,行程自己送上門

FOR ENGINEERS · 想深入的人看這裡

技術邏輯拆解:這些設計,為什麼要這樣做

前面看的是「做了什麼」;這一段看「怎麼設計才安全、才不出錯」。四個真正的關鍵機制。
Webhook 驗簽 短效 HMAC Token Reply vs Push 推播去重 · 排程代理
機制 1 · Webhook 守門

收訊息的兩道門:先驗真、再快回

門一 · 驗真

驗簽要「Fail-Closed」

只要簽章、原始 Body 任一缺少,或比對不過——一律拒絕(回 401),不是「缺資料就放行」。

  • 用 timing-safe 比對,防時間差破解
  • 沒設定金鑰?寧可讓 Webhook 直接停用
門二 · 快回

先快回 200,再背景處理

Webhook 要在極短時間回 200,否則 LINE 會判逾時重送同一則,造成重複處理。

  • 驗簽後把慢工作(查 DB、推播、稽核)丟背景佇列
  • 只有需要 replyToken 的即時回覆才當場做
小細節:LINE 驗證 Webhook 時可能送來空事件,你的系統也必須回 200,否則設定畫面會顯示失敗。
機制 2 · 短效連結

打卡連結為什麼「30 分鐘後就沒用」

Token 內含什麼
員工 ＋ 操作類型 ＋ 到期時間
＋
用密鑰簽章(HMAC)
無狀態:伺服器不用存,重啟仍能驗

為什麼這樣就安全

  • 過期即失效——到期時間寫在 Token 裡
  • 被轉傳也沒用——時效一過就作廢
  • 被竄改就對不上——簽章驗不過直接拒絕
同一招也用在綁定連結:一次性、用過即失效。
切記:別把「LINE User ID」直接當身份憑證塞在網址——那不是可驗證的身份。
機制 3 · 回訊息的兩種方式

Reply 還是 Push?用錯就發不出去

Reply · 即時回

用當下訊息帶來的 replyToken。

  • 一次性、短時效、免費
  • 票券過期或用過就失效
  • 適合:使用者剛傳訊息、要馬上回

Push · 主動推

用對象的 userId,隨時可發。

  • 可隨時觸發、計入訊息用量
  • 單發 Push、群發 Multicast
  • 適合:非即時的通知、提醒、完成回報
用途
不同
最常見的陷阱:打卡「完成後」想回一則通知,卻還想用 replyToken——但那張票券早已失效。此時沒有即時對話,必須改用 Push(to: userId)。時機用錯,訊息就默默發不出去。
機制 4 · 讓自動化「剛剛好」

主動推播,難在「不吵、不漏、追得到」

公告 · 不重複發

去重規則 + 可追蹤

  • 只在「第一次進入已發佈」才推;編輯不重發、封存不發
  • 群發 Multicast 每批 500,自動分批
  • 進階:建「通知紀錄表」記批次/收件數/狀態,失敗可重試
因為「公告成功 ≠ LINE 已送達」,要看得到結果才追得到問題。
早報 · 排程代理

cron ＋ 行事曆代理

  • cron 每天固定 08:00 觸發
  • 用服務帳號 代理(DWD) 以唯讀讀員工行事曆
  • 整理今明兩天、標出時間衝突,用 Push 個別推
注意:別讓多個程序同時跑同一個排程——會重複發給同一個人。
先判斷,再動手

什麼情境,值得把它串進 LINE?

高頻、重複的動作

每天都在做的事(打卡、回報、丟檔),自動化最划算。

人已經在 LINE 上

對象本來就用 LINE,不必逼他們換工具。

需要「主動通知」

有時效的提醒、公告,推播比等人查更有效。

資訊要收集彙整

散落的檔案、回報,想集中成一份可查的資料。

反例:一年才用一次、對象根本不看 LINE、或流程本身還沒想清楚——先別急著串。
你自己能做嗎

DIY 門檻其實不高,分三層走

要備齊什麼

三樣東西

  • 一個 LINE 官方帳號 + 開通 Messaging API
  • 一個能收 Webhook 的後端
  • 一個放資料的地方(雲端／DB)
先做得到

規則型:先跑起來

用關鍵字、檔名規則就能分類歸檔、回罐頭訊息。無 AI 也能上線,速度最快。

再變聰明

AI 型:加上判讀

接上 AI 去讀內容、判斷語意、自動摘要分類——需求明確後再加,不必一步到位。

呼應課程主軸「先試再買」:先用規則型花小錢試出價值,確認流程對了,再投資做聰明。
上線前一定要顧

方便的另一面:五條安全底線

1 · 密鑰只放後端

Token、金鑰絕不放前端、不進 Git、不貼群組截圖——外洩就是別人能冒充你發訊息。

2 · Webhook 一定驗簽

每一則進來的訊息都要驗證確實來自 LINE,不能只靠來源判斷。

3 · 測試與正式分開

用不同官方帳號,避免測試訊息誤發給真實員工或客戶。

4 · 推播用量要估算

主動推播會計入官方帳號額度,上線前先算清人數 × 頻率。

第 5 條最重要:密鑰一旦懷疑外洩,立刻換發、撤銷舊的——寧可麻煩,不要僥倖。
